# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project Overview

**Draw-Anything** is a collaborative whiteboard / diagramming app: Next.js 15 (App Router), React 19, TypeScript, Tailwind 4. Real-time editing runs on Liveblocks, persistence and users on Convex, auth on Clerk. It has a custom orthogonal arrow-routing engine (`core/routing`) and an AI diagram generator built as a LangGraph multi-agent pipeline (`features/ai/server`).

## Commands

```bash
npm run dev              # Dev server (Turbopack was removed from the script)
npm run build
npm run lint             # next lint
npx tsc --noEmit         # Type check

npx vitest run                       # All unit tests (there is no `npm run test` script)
npm run test:browser                 # Real-Chrome text checks (excluded from the line above)
npx vitest run <file>                # One file
npx vitest run -t "<test name>"      # One test by name

npx convex dev           # Convex dev server; regenerates convex/_generated
npx convex deploy
```

Tests live next to source (`*.test.ts`) under `core`, `features`, `lib`. Browser tests (`tests/browser`) bundle real modules via `harness.ts` (`openPage({ secure, ui })`: `secure` serves from localhost so the Clipboard API exists, `ui` adds real React components on `window.U`). `vitest.config.ts` maps the `@/` alias. They are pure-logic tests (no DOM or React renderer is installed): hooks and components are covered through the pure modules they delegate to, so browser behaviour still needs a manual check. `package-lock.json` matches `package.json` again (`npm ci` works). `npm run lint` is clean; `next build` needs `NEXT_PUBLIC_CONVEX_URL` and Clerk keys set to prerender.

## Architecture

### Directory layout
- `app/` — routes: `(main-page)` dashboard/billing/org creation, `whiteboard/[id]` editor, `api/` (AI generation, Liveblocks auth), `actions/` server actions. The Clerk webhook lives in `convex/http.ts` only.
- `features/` — feature modules: `whiteboard` (editor UI + hooks), `dashboard`, `billing`, `ai` (client types/schemas + `server/` pipeline), `diagram-code` (text DSL ⇄ canvas).
- `core/` — framework-free engine code: `shapes` (shape registry, per-shape definition/render/hit-test), `routing`, `arrow` (React hook bridging elements → routing), `anchors`, `snap`, `collision`. `shapes/base/resize-box.ts` is the one resize implementation; shapes must delegate to it.
- `convex/` — schema and queries/mutations. `liveblocks.config.ts` — Liveblocks room types and hooks.

### Whiteboard data flow
- **Liveblocks storage is the live document**: `elements: LiveList<LiveObject<DrawingElementJson>>`, plus presence (cursor, selection, pencil draft). See `liveblocks.config.ts`.
- **Convex `whiteboards.content`** is a JSON snapshot. On load, `use-whiteboard-page-controller.ts` seeds an empty Liveblocks room from it and restores the viewport; `features/whiteboard/hooks/data/use-whiteboard-auto-save.ts` writes it back.
- **Authorization** is one rule: the whiteboard's creator, or a member of its organization (`convex/lib/accessRules.ts`, enforced by `convex/lib/access.ts` in every whiteboard/AI-frame/memory function). Non-members get nothing (there is no share-link feature). `app/api/liveblocks-auth/route.ts` applies the same rule through `lib/authz/room-access.ts` and fails closed. Convex auth uses the Clerk JWT template named `convex` (`convex/auth.config.ts`); org-wide access needs an `org_id` claim in it. Users are created by the Clerk webhook in `convex/http.ts` and on client login (`users.storeUser`). Deploy Convex before the app when changing these rules.
- **Autosave** is `data/autosave-controller.ts` (pure: whole-board change detection, single flight, debounce + max wait, retry with backoff, stops on permission errors, flushes on hide/unmount) driven by `use-whiteboard-auto-save.ts`. It does not run until the Liveblocks room has been seeded from the stored snapshot (`seedState`), so a not-yet-synced empty board never overwrites stored content; unparseable stored content (`saved-content.ts`) is left alone.
- **Undo**: every drag/resize/erase/draw gesture is bracketed by `beginGesture`/`endGesture` (`interaction/gesture-history.ts`, an idempotent wrapper around Liveblocks `history.pause/resume`) so it is one undo step.
- **Canvas input**: `whiteboard-canvas-stage.tsx` uses pointer events with pointer capture (primary button/pointer only); selection rules are in `interaction/selection.ts`; Escape runs `cancelDrawing` before clearing the selection. Connector-handle arrows are built by `interaction/connector-arrow.ts` and routed through the same obstacle-aware router as drawn arrows. Unfilled `isGuide` rectangles (AI group frames) are hit-tested on their border only.
- **Router** (`core/routing`): the per-edge search tries fixed path shapes, then `grid-route.ts` (a deterministic Hanan-grid search around obstacles), and only then accepts a path through a node. `pinPathEndpointStubs` must never overwrite a real bend with the stub point (it once sent connectors straight through other rows).

### Text (`core/text`)
One typography source (`typography.ts`: font stack, line height 1.2, `makeFontString`); canvas drawing, measuring and both DOM editors read it, so entering edit mode moves nothing. Shape-label layout (`label-layout.ts: layoutShapeLabel`) is computed in world units and only scaled by zoom afterwards, so a label wraps the same at every zoom; `measureShapeLabel`/`renderShapeLabel` are the screen-space adapters. Wrapping code takes a `MeasureContext` (`font` + `measureText`), so tests and the server can pass a double. `estimate.ts` sizes text without a canvas (AI compiler, tests); it is an estimate of Inter, not real metrics. `resizeText` takes its size from the already-measured `originalBounds`; do not re-measure there. Canvas text sits on the CSS first baseline (`baseline.ts`); both editors' styles live in `shape-label-editor-style.ts` / `text-block-style.ts` and `label-region.ts` is the one place that says where a label goes (semantic nodes keep theirs beside the icon). **The app does not load Inter**, so users get their system font, whose widths are not linear in size; exact zoom and resize behaviour is only guaranteed for Inter (see the spec). Text tests: `core/text/*.test.ts`; real-Chrome checks (canvas vs editor pixels, caret, IME, estimator accuracy) run with `npm run test:browser` (system Chrome via `playwright-core`; skips if none, set `CHROME_PATH`; `tests/browser/fixtures` holds Inter for the tests). Design: `docs/superpowers/specs/2026-10-15-text-foundation-design.md`.

### Icons (`core/icons`)
`registry.ts` is the only icon source: `iconForNode(element.ai)` = valid `ai.icon`, else `ai.semanticKind`, else generic (old boards need no migration). Vendor words are aliases of neutral ids; add icons with `registerIcon`. Glyph paths are vendored lucide (ISC) generated by `scripts/generate-icon-glyphs.mjs` into `glyphs.ts` (never edit by hand; keep each shape a separate path string). `draw.ts` draws the tile at any zoom and falls back to a text badge. Icon geometry still belongs to `core/text/label-region.ts`. The registry has a curated core (`add()` lines, `glyphs.ts`: always loaded, the only icons an AI prompt lists) and a **library loaded on demand** (`library.ts`: `catalog.json` lists about 400 more lucide icons as `glyph|alias,alias` per category, `glyphs-extra.ts`, and `logos.ts`). `loadIconLibrary()` installs it once (a separate ~350 KB chunk); the stage loads it when a board uses an icon the core cannot resolve (`needsIconLibrary`) and redraws on `iconLibraryVersion`, the picker loads it on open, export awaits it. Installing never overrides an existing id or alias, so old boards and AI diagrams do not change. Brand marks: `logos.ts` (204, generated by `scripts/generate-logo-glyphs.mjs` from Simple Icons, CC0 data, trademarks stay their owners') register as `logo-<slug>` icons (`style: "logo"`: filled glyph in its own colour on a white tile); vendor words stay aliases of the neutral glyphs, so old AI boards do not change. Simple Icons no longer ships AWS, Azure, OpenAI or Slack, so those come only through custom icons. Custom icons (`custom-icon.ts`): an imported SVG keeps only basic-shape geometry and one colour, is stored inside the element as `ai.customIcon`, and is re-validated by `validateCustomIcon` on every read (`iconForNode`); the picker remembers them per browser in localStorage. Design: `docs/superpowers/specs/2026-10-16-icon-system-design.md`.

### AI diagram agent (`features/ai/diagram-agent`)
An alternative to the 12-agent workflow, selected with `AI_PIPELINE=agent` (default `legacy`; `pipeline.ts`). One loop (`agent-loop.ts`): the model writes diagram code (the `features/diagram-code` DSL) and may call three string-only tools: `search_icons` (`core/icons/registry.ts: searchIcons`), `check_diagram` (parse + layout dry-run + design lint: `tools/check-diagram.ts`, `tools/lint.ts`) and `finish`. Two interchangeable transports (`transports/`): `native` (LangChain `bindTools`, groq/openai/anthropic/openrouter/local) and `text` (a lenient `<tool name=...>` + fenced-code protocol, always for Gemini and the automatic fallback when a provider rejects `tools`); `AI_AGENT_TRANSPORT=native|text` forces one. Tool calling here is plain-string arguments with server-side lenient validation, so the "no provider-native structured output" rule above still holds. History is shrunk before every request (`compactHistory`: diagram code in turns before the latest reply is replaced by a marker and long reviews are cut, but every call, icon lookup and call/result pairing stays; dropping whole turns made gpt-oss repeat its lookups until the turns ran out). `search_icons` takes several comma-separated terms in one call, turns that only search do not use the turn budget (up to `MAX_LOOKUP_TURNS`), and rate-limit retries wait the provider's own "try again in Ns" (`retryAfterMs`). Live finding on Groq's free tier (gpt-oss-120b, 8,000 tokens per minute): runs are limited by tokens per minute, not by prompt size alone. Any parseable draft is kept; only "nothing readable was ever produced" throws. `run.ts` emits the same `AIStreamEvent` contract as the legacy workflow (frame.created -> phase.* -> element.batch -> frame.done), so the client and route handler are unchanged. Prompts: `prompt/` (system prompt, per-diagram-type playbooks, worked examples that tests assert parse and lay out cleanly). Quality is measured, not claimed: `npm run eval:ai` (live provider calls, keys from `.env.local` or `.env`; `AI_EVAL_DELAY_MS` paces runs for free-tier token limits; `AI_EVAL_PROVIDERS`, `AI_EVAL_TRANSPORTS`, `AI_EVAL_LEGACY=1`, `AI_EVAL_LIMIT`) writes `docs/superpowers/reports/ai-eval-<date>.md`. Design: `docs/superpowers/specs/2026-10-16-ai-diagram-agent-design.md`.

### Canvas interaction (`features/whiteboard`)
Logic lives in pure, tested modules; hooks only wire them. Shortcuts: `hooks/interaction/keyboard-policy.ts` (`resolveShortcut`; nothing fires while typing, read-only viewers get no editing commands), dispatched by `use-whiteboard-keyboard.ts` and `runShortcut` in the controller. Viewport: `utils/viewport-math.ts` (cursor-anchored zoom, fit capped at 100%, plain wheel pans, Ctrl/Cmd+wheel zooms; the wheel listener is native and non-passive because React's `onWheel` cannot `preventDefault`). Dragging: `interaction/drag-session.ts` (`computeDrag`: position = origin snapshot + total pointer travel, snapped to other shapes' edges/centres within 6 screen px, Alt disables; guides drawn by `utils/draw-guides.ts`). Copy/paste/duplicate/nudge/align/distribute/z-order: `utils/arrange.ts` + `utils/clipboard.ts` through `use-element-commands.ts`, each a single batched Liveblocks mutation (`addElements`/`updateElements`/`reorderElements`, one undo step; array order is z-order). Pasted copies drop `ai.semanticId/frameId/generationId`. Minimap: `utils/minimap-math.ts` + `components/canvas/minimap.tsx`. The real editor runs in Chrome without Clerk or Convex: `tests/browser/editor/open-editor.ts` (`openEditor()`) bundles the actual page with in-memory fakes of Liveblocks (real `LiveObject`/`LiveList`), Convex and Next, and exposes the controller on `window.__editor`; `editor/*.browser.test.ts` drive it with real pointer and keyboard input. Signed-in behaviour (Clerk, real Convex/Liveblocks, two clients) is still untested. The pure modules are unit tested and `tests/browser/canvas-ux.browser.test.ts` checks the math on a real canvas.

**Editing model.** Manual rectangle/ellipse/diamond are created blank (no `"TEXT"` label); old boards keep their labels. Double-click, or Enter on a single selected shape, calls `controller.beginEditing` (text blocks and shape labels). In the label editor Enter is a newline, Escape / Ctrl or Cmd+Enter / click outside commit (never cancel), the caret opens at the end, and clearing the text deliberately blanks the shape. After drawing a shape, line or connector the tool returns to select and the new element is selected (freehand and eraser stay active); a click without a drag creates nothing.

**Connectors.** The arrow tool attaches both ends: `useMagneticSnap.findNearestSnap` (in `core/snap`) first snaps to the nearest anchor within `radius` (callers pass `CONNECTOR_SNAP_PX / zoom`, so it is screen pixels), then falls back to the nearest anchor of the topmost shape whose bounds contain the point (arrows, lines and freehand are never targets). A new arrow with both ends bound is routed through `routeConnectedArrow` when it is committed; hovering shows the snap preview. Clearing a field in a Liveblocks write must go through `writeElement` (`LiveObject.update` ignores `undefined`, which used to make disconnecting an arrow end a no-op). Grabbing a selected arrow's end wins over the target's connection handle.

**Shapes and icons.** `ellipse` is a box-fitted ellipse (the toolbar and `C` use it); `circle` (centre + radius) stays only so saved boards still render. Corner radii live in `core/shapes/base/geometry-tokens.ts`; label-box fractions for circle/ellipse/diamond live in `core/text/label-region.ts` and are shared by renderers and the editor. The icon picker (`I`, sidebar, command menu; `overlays/icon-picker.tsx`, pure logic in `utils/icon-picker.ts`) inserts a standalone `icon` element (`core/shapes/icon`: just the glyph, no node box, no label; `ai.icon` or `ai.customIcon` names it; line icons take the element colour, logos keep theirs on a white tile) at the viewport centre. Semantic nodes with an icon tile remain what AI diagrams draw. Logos and the user's own SVG icons appear under their own picker tabs. Design: `docs/superpowers/specs/2026-10-16-canvas-ux-design.md`.

**Pointer gestures.** Per-gesture working data lives in one `GestureScratch` (`interaction/gesture-scratch.ts`) cleared by a single `resetScratch()`; decisions that need no React state are pure and tested (`startDragSession`, `resolveConnectionDrop`, `classifyDraftCommit`, `growDraftElement`, `editBendAtPoint`). `use-whiteboard-drawing.ts` holds one `Gesture` (`gesture-state.ts`: idle, drawing, erasing, dragging, resizing, marquee, connecting) instead of independent booleans; a pointer-down while one is still active means its pointer-up was lost, so `resetStaleGesture` finishes the leftovers first. **Touch and hit-testing.** Two fingers (touch pointers only, tracked in the stage) pan and zoom through `pinchView`; a second finger drops a shape being drawn. Line, arrow and freehand pick distance is `screenTolerance(px, zoom)`, constant in screen pixels, and connector snap radius is `CONNECTOR_SNAP_PX / zoom`; handles are drawn from the same `getShapeResizeHandles` list the pointer tests (freehand has none). Touch is verified with CDP-emulated touch in Chrome, not a device.

**Comments.** Pinned threads live in Convex (`comments` table, `convex/comments.ts`; same board access rule via `requireWhiteboardAccess`, text/position/delete rules in `convex/lib/commentRules.ts`). `M` is the comment tool; `components/canvas/comment-layer.tsx` draws pins over the canvas (screen position = `worldToScreen`, so they follow zoom and pan), the composer (Enter sends, Shift+Enter newline) and the thread card (reply, resolve/reopen, delete own). Resolved threads are hidden behind a "Show resolved" chip. `@` in the composer suggests participants (the board's creator and everyone who has commented; Convex cannot list an organization's members, Clerk can), the server keeps only valid ones, and a pin that mentions you says so; there is no push or email notification. Convex functions are tested for real with `convex-test` (`convex/comments.test.ts`: access, org claims, delete rules, mentions). Deploy Convex before the app: the client calls `api.comments.*`. `convex/_generated/api.d.ts` was edited by hand to list the module; `npx convex dev` will regenerate it.

**Theme contrast.** `core/color/theme-contrast.test.ts` parses `app/globals.css` and fails if a foreground/background token pair drops below WCAG AA (4.5:1 text, 3:1 focus ring) in either theme; `resolveTextColor` also enforces 4.5:1 on shape labels. Change tokens, not components.

### Export (`features/whiteboard/export`)
One renderer: every format draws elements with `drawElement` in light mode (`core/theme/render-theme.ts: withRenderTheme`, because several renderers read the page's `dark` class) with no editor state. `SvgContext` (`svg-context.ts`) is a recording stand-in for `CanvasRenderingContext2D`: it emits the SVG and measures the real ink, so bounds come from what was drawn (strokes, arrowheads, text), never from a guess. `export-scene.ts: exportScene` does pass 1 into `SvgContext`, then PNG and PDF draw the same elements onto a canvas inside that box plus a 24-unit margin. PDF is a raster single page (`pdf.ts`, no dependency); SVG is vector with no `<image>`/`<script>`/`href`/external `url()`; colours, fonts and path data are allow-listed and text is XML-escaped. Selection policy (`selection-policy.ts`): selected + connectors with both ends selected + their labels. Limits in `EXPORT_LIMITS`; failures are `ExportError`s shown in `components/overlays/export-dialog.tsx`; `hooks/export/use-board-export.ts` runs one export at a time with cancel. Renderers must not call `drawImage`/load images (it would taint the export canvas) and a new canvas call must be added to `SvgContext` (unsupported calls throw on purpose). Opened from the command menu or Cmd/Ctrl+Shift+E. Verified in real Chrome (`tests/browser/export*.browser.test.ts`); the signed-in editor wiring is not covered by any test. Report: `docs/testing/export-test-report.md`.

### Shapes
`core/shapes/<shape>/` each export a definition built with `createShapeDefinition` (bounds, hit-test, resize handles, canvas render, anchors). They are registered in `core/shapes/register-shapes.ts` / `shape-registry.ts`; add new shapes there.

AI flowcharts draw `decision` as a `diamond` and `start`/`end` as a `pill` (a rectangle with fully rounded ends, `core/shapes/pill`; also on the toolbar as "Terminator"), everything else as a `semantic-node` with an icon tile. `shapeOf` in `canvas-compiler.ts` decides (an explicit `shape:` beats the kind), `sizeDiamondNode`/`sizePillNode` in `core/text/node-size.ts` size each so its label fits (the pill's label box is `pillLabelBox` in `core/text/label-region.ts`, shared by renderer, sizing and layout metrics). In the DSL `shape: diamond|pill` (`oval` and `ellipse` read as pill) is accepted; the serializer only writes `shape:` when the kind does not already imply it. `graphFromElements` reads an explicit node `color:` back (stroke plus `tint(stroke, 0.88)` fill, unless it is the kind's own colours via `kindColors`), so regenerating code keeps it. A new node-like element type must also be added to `isNodeElement` (`layout/metrics.ts`), `NODE_TYPES` (`diagram-code/canvas.ts`) and the node list in `diagram-code/pins.ts`. The agent prompt is trimmed per request (`prompt/prompt-context.ts`: inferred diagram type picks the playbook, one example and the icon categories); its size budgets are tests in `prompt/prompt-context.test.ts`.

### Routing engine (`core/routing`)
Public API is `orthogonal-router.ts` (`routeArrowPoints`, `routeArrowBatch`); `route-engine.ts` (`routeWithEngine`) runs the pipeline. `orthogonal-router.ts` does not re-export the engine (it would be a cycle: import `routeWithEngine` etc. from `route-engine.ts`); endpoint stub pinning and re-anchoring live in `endpoint-stubs.ts`, bend/segment editing in `path-editing.ts`, shared types (`RouteEngineEdge`, `RoutingObstacle`) in `types.ts`. `core` must not import from `features` (`getAdaptiveColor` is `core/color/adaptive-color.ts`):
1. Sanitize inputs (`routing-guards.ts`: `sanitizeEdges`, `sanitizeObstacles`, `isFullyConnectedEdge`)
2. Dirty tracking against `RouteEngineState` (route cache, path-hash cache, congestion map). An edge is re-routed if marked dirty, uncached, or its hash (endpoints, handles, mode, existing points, obstacle layout) changed. The engine routes whatever subset it is given and never infers deletions; the state's owner calls `pruneRouteEngineState(state, liveArrowIds)` (the hook does, on every `elements` change)
3. Parallel-edge offsets (`parallel-edge-manager.ts`)
4. Per-edge A* obstacle avoidance + candidate scoring (`obstacle-avoidance.ts`, `congestion-map.ts`)
5. Segment conflict resolution (`segment-conflict-resolver.ts`, spatial index)
6. Lane assignment (`lane-manager.ts`) and crossing minimization (`crossing-minimizer.ts`)
7. Normalization (`path-normalizer.ts`) and endpoint stabilization to connection handles

Path rules that the tests in `core/routing/endpoint-approach.test.ts` enforce for every anchor pairing: a path starts and ends exactly on its anchors, leaves/arrives straight out of the shape's side (`meetsAnchorsCleanly`, applied to every candidate in `obstacle-avoidance.ts`; the source and target are ignored by the obstacle test, so without it a path from a left anchor to a target on the right ran through its own shape), and the grid snap in `path-normalizer.ts` never moves the first or last segment off its anchor (it used to leave a short jog at the shape). A manual route is kept only while it still meets those rules, else the arrow is routed afresh. Manual editing (`core/shapes/arrow/interaction.ts`): dragging a terminal segment slides the lane it leads to (never to the wrong side of the anchor, `MIN_STUB`), inner lanes next to an endpoint are clamped the same way, and the editor computes every frame from the element as it was when the drag began (`resizeBaseRef`), so inserted or merged points cannot re-index the grabbed segment. `getElementBounds` returns cached bounds only for the stored element object: a moved copy is measured fresh (the cache used to return last frame's bounds, leaving connected arrows one pointer-move behind and detached after the last move). `routingMode: "straight"` arrows bypass stages 6–7 (they would otherwise be forced to Manhattan geometry). `normalizeRoutes` checks crossings per arrow via `createCrossingCounter` (one grid, no map clones); do not reintroduce a whole-graph `countTotalCrossings` per arrow.

`core/arrow/use-arrow-connections.ts` feeds it from React: it only routes descriptors passing `isRouteDescriptorReady` (arrows mid-drag can lack `sourceId`/`targetId`/points), and keeps a second module-level cache, `globalPathCache` (`path-cache.ts`), keyed by arrow id + rounded endpoints + obstacle signature.

Rule: always guard points with `isValidPoint` / `toValidPoint` from `routing-guards.ts` before reading `.x`/`.y`. Routing must fall back to a straight path, never throw.

Point = `{ x, y }`; ConnectionHandle = `"top" | "right" | "bottom" | "left"`; descriptor type is `RouteArrowDescriptor` in `orthogonal-router.ts`.

### AI diagram generation (`features/ai/server`)
- Client (`features/whiteboard/hooks/controller/use-ai-generation.ts`) POSTs to `/api/ai/generate-diagram` and reads a Server-Sent Events stream. It also records frame progress in Convex (`convex/aiFrames.ts`).
- `workflow.ts` builds a LangGraph `StateGraph`: contextRetriever → architecturePlanner → domainModeler → infrastructureExpander → relationshipAgent → diagramComposer → layoutAgent → validationAgent → criticAgent → (one optional expansion loop back to relationshipAgent) → repairAgent → canvasCompiler. Agents are in `agents/`, prompts in `prompts/`, deterministic helpers in `tools/`.
- Agents emit `AIStreamEvent`s in their state updates; the route forwards them and also emits v1 compatibility events (`sse.ts`).
- The route (`app/api/ai/generate-diagram`) requires a Clerk session, validates and size-limits the body (`request-guard.ts`), allow-lists the provider, rate limits per user (in memory, per server instance; `AI_RATE_LIMIT_MAX` default 10 per `AI_RATE_LIMIT_WINDOW_MS` default 10 min), and shows clients only generic error text. `GET` on the same path lists the providers that have keys configured; the UI offers only those. Logic is in `generate-diagram-handler.ts` because route files may only export HTTP handlers.
- Structured model output works the same for every provider: the JSON Schema (`z.toJSONSchema`, `buildJsonInstruction`) goes in the prompt, the reply is read as plain text (`createPromptedStructuredModel`, `json-extract.ts: parseModelJson`) and normalised leniently (`schemas.ts`: clamps to `MAX_GRAPH_*`, drops unusable items with warnings, throws only if no node survives), with one corrective re-ask for unreadable *or* unusable answers (`agents/types.ts: callStructuredNormalized`). **Do not use a provider's native `withStructuredOutput`** (tool calling, Groq strict `json_schema`): it validates against the strict Zod schema before the normaliser runs and turned every null/over-long field into a failed generation. Do not reintroduce strict `.parse()` of model output. Unreadable replies are logged with the model's own text (`[callStructured] … gave no readable JSON`). The critic's layer-completeness rules apply to `architecture` diagrams only.
- `canvas-compiler.ts` is a pipeline: `prepareDiagram` (node sizes from labels via `core/text/node-size.ts`, cycle-aware layers, group paths, gaps) -> a `PlacementEngine` (`layout/layered-placement.ts`: components laid out separately, `layered-order.ts` barycentre sweeps with nested groups kept adjacent, row heights from the tallest node, room between same-row neighbours for edge labels, `group-separation.ts` moves strangers out of group frames) -> `buildCanvas` (frames, routing through `core/routing`, `layout/bus.ts` shared bus levels for fan-out/fan-in, `layout/handle-selection.ts` which side each edge leaves (a decision's side branches leave from its left/right corner), and a last `assignCenters` pass that straightens one-to-one chain links with a small offset (`SMALL_JOG`), `layout/edge-labels.ts` collision-free label placement). Node height is dynamic (min 78, 92 for decisions); never reintroduce a fixed height. `compileAIDiagramDetailed` returns diagnostics (colliding labels, dropped groups, unfitted nodes, layout fallback to `grid-placement.ts` if an engine throws). `pins` keep user-dragged nodes in place when diagram code is re-applied (`features/diagram-code/pins.ts`). Group frames and edge labels are `isGuide` elements with `ai.role`; a frame is omitted rather than drawn over a non-member. Quality is measured by `layout/metrics.ts` (geometry only); `layout/benchmark/` compares the engine with ELK.js (dev dependency, not used in production) and asserts the guarantees. Decision and numbers: `docs/superpowers/reports/2026-10-16-layout-benchmark.md`. Measurement contract (world vs screen, estimator vs browser, Geist is DOM-UI only) is in the Sub-project B spec.
- `features/diagram-code` is an Eraser-inspired text DSL (not claimed compatible): `parseDiagramCode`, `serializeDiagramCode`, `elementsFromDiagramCode`, `graphFromElements`. Edited from the AI panel's Code tab; applying it to an existing diagram is one undo step.
- `model-providers.ts` picks the LLM from the request's `provider`: gemini (default), groq, openai, anthropic, openrouter, local. Each reads `<PROVIDER>_API_KEY` and an optional `<PROVIDER>_MODEL` override (`LOCAL_AI_*` for local).
